# DeskFuse: empirical 800x600 effective-desktop scaling ceiling

**Date:** 2026-10-19  
**Status:** evidence / hypothesis, not a documented Windows API contract  
**Development target:** Approach A only — Windows desktop and captured frame at exact 1440x3120, genuine 350%/336 DPI for independent PMv2 native windows, 100-DIP ruler 350x350 captured pixels. No oversized backing desktop, resize, or crop.

## Evidence

FocusIdd driver protocol 2 on the user's Windows 10 test PC, with real monitor topology checks. The read-only modes never perform a DPI scale SET. Different virtual EDID physical diagonals (80/170/420 mm) changed the default/recommended scale without changing the maximum.

| Virtual mode | -3 maximum | Effective desktop at maximum (DIPs) |
| --- | ---: | ---: |
| 1440x3120 | 225% | 640x1386.7 |
| 1440x3900 | 225% | 640x1733.3 |
| 1600x3120 | 250% | 640x1248 |
| 1920x3120 | 300% | 640x1040 |
| 2100x3120 | 350% | 600x891.4 |
| 3120x1440 | 225% | 1386.7x640 |
| 2560x1080 | 175% | 1462.9x617.1 |
| 1200x1200 | 150% | 800x800 |

The measurements match the largest Windows scale ladder step such that
`min(width,height) / (percent/100) >= 600` **and**
`max(width,height) / (percent/100) >= 800`.

This is stronger than a simple 600-DIP *width* hypothesis: rotation yields the same cap for 3120x1440, and a square 1200x1200 caps at 150% rather than the 200% predicted by a 600-DIP short-side-only rule. The exact numbers 600 and 800 are **not independently proved** by these coarse scale-step samples. The model is not a guarantee on another Windows build.

## Independent real-window results

**2100x3120, supported 350%:** `-3 current=350%, max=350%`, effective monitor DPI=336, independent native Win32 PMv2 `GetDpiForWindow=336`. Historical WinForms probe still reported 96 DPI, and should not be used alone to judge native DPI. Independent native 100-DIP captured ruler has been implemented on this branch, but awaits hardware validation.

**1440x3120, explicitly unsupported -4 requesting 350%:** `-3 current=350%, max=225%` but independent native Win32 PMv2 `GetDpiForWindow=216`, monitor DPI=216, WinForms=96. A successful -4 API return and stored value DO NOT establish native 350% rendering. The virtual display was removed and physical displays were unchanged.

**Goal at 1440x3120/350%:** effective desktop 411.4x891.4 DIPs, below the inferred short-side >=600 DIPs constraint.

## Engineering implication

Do not repeat EDID physical-dimension tuning or undocumented -4 overrides as if they solved native 350% DPI. A normal FocusIdd display connected to Windows appears constrained by effective desktop geometry. An alternative architecture is not verified, and no implementation can claim Approach A succeeds until a native PMv2 window on the **exact 1440x3120** monitor both reads **336 DPI** and paints a **350x350 physical-pixel** 100-DIP ruler into an **unresized 1440x3120** frame. Native video capture, encode/decode latency, and 1:1 frame transport are separate acceptance requirements.

The experimental scripts use an installed known-good driver; no driver installation, physical-display mutation, registry writes, or independent system rollback is performed. Keep main and acceptance integrations untouched.

## Additional Arena.ai replies (3.md and 4.md)

- **3.md** independently recognizes both the 600-DIP short-side and 800-DIP long-side conditions. Its proposed 2100x2800 and 2100x2700 modes correctly separate the inclusive 800-DIP boundary from a mode below it. This is a testable prediction, **not direct proof of the internal Windows algorithm or the named dxgkrnl/win32kbase implementation**.
- **4.md** appropriately cautions that the observed scaling ceiling is an empirical heuristic and correctly distinguishes native pixel dimensions from EDID physical millimeters. However, its formula `W/scale >= 600` is only valid for portrait modes where the long edge is not binding: it fails to predict the independently observed cap of 150% on a 1200x1200 square.
- Claims in 3.md that all custom-scaling and registry overrides are kernel-clamped are unsupported by supplied diagnostic evidence. We will **not** apply per-user/system-wide registry hacks or custom DPI settings that could affect physical displays or require logoff.
- Browser zoom achieves a smaller CSS viewport **for browser content only**. It is not per-monitor 336-DPI delivery to arbitrary Windows programs, and does not meet Approach A.

## Public Windows documentation vs. our measurements

- Microsoft Win32 UX guidelines: https://learn.microsoft.com/en-us/windows/win32/uxguide/vis-layout recommend support for **800x600 minimum effective resolution**. Those are application layout guidelines, **not proof** of a DPI-scale calculation embedded in a particular kernel file.
- GetDpiForWindow: https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getdpiforwindow documents that per-monitor-aware HWND DPI is the monitor DPI, making the independent native checker appropriate.
- GetDpiForMonitor: https://learn.microsoft.com/en-us/windows/win32/api/shellscalingapi/nf-shellscalingapi-getdpiformonitor warns against using it alone from a PM-aware caller; raw/supplementary readbacks cannot supersede an independent native PMv2 window and captured ruler.
- IddCx DISPLAYCONFIGPATH2: https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/iddcx/ns-iddcx-iddcx_displayconfigpath2 documents `MonitorScaleFactor`, but explicitly calls it a *hint* the OS can override to maintain a valid session. It requires **Windows 11 22H2 September Update / IddCx 1.10**, so it is not an immediate supported override on our Windows 10 test PC. It also requires driver work, forbidden while the shared known-good driver is in use.
- Supported RDP properties: https://learn.microsoft.com/en-us/azure/virtual-desktop/rdp-properties lists 100/125/150/175/200/250/300/400/500, **not 350**, for the deprecated `desktopscalefactor`; this is not a proven workaround.
