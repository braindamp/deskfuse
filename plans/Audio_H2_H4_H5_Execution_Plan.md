# DeskFuse audio handover execution plan

6 November 2026. Source baseline `ad8084b` on `main`. This plan covers the remaining H2 barrier, the H3 first-device check, H4 handover, and H5 qualification. It follows the [reviewed handover decision](Audio_Handover_Reviewed_High_Decision.md) and the [N1–N6 ownership plan](Native_Audio_Owner_Boundary_High_Handoff.md).

## What the current code proves

- H3 has a debug-gated independent Android service with explicit Start and Stop, a single enrollment writer, a selected-network socket, and matched first-output readiness. The ARM64 build and 62 Android unit tests passed. An audible first delivery on that artifact still needs device evidence.
- The Windows runtime has one listener reader, a bounded candidate worker, and a tested first-delivery adoption path. `Runtime::forward_active` rejects `PREPARE`, `ISSUE`, and `PROOF`. `BrokerCommittedAudioSource` starts the dispatcher in acquisition-only mode. The Rust and C# pinned-issue parsers accept first attachment only. Opening a flag alone cannot safely enable handover.
- `SourceOwner::fence_delivery_at` drops the delivery and its sealed egress and takes a source fence. It also enters reconnect grace and retains a pending close. Replacement needs explicit retirement semantics so a committed cutover cannot accidentally enter the transport-loss path or wait on unrelated close bookkeeping.
- Android's `Session::play` owns the renderer and receiver for a single connection and runs under the session lock until playback returns. Starting a second copy of this path would restart AAudio and lose receiver history. `AudioPhoneRequests` and the broker already have the exact-result primitives. H4 needs to carry the same request owner and the same native playback state across the transition.

- The H3 debug service requests two AAudio bursts. Use it as an identified development profile. H2 source work can proceed while the smoke-test inputs are assembled. A source or build result and a hardware result have separate exit criteria.

## 2. Land the H2 Windows retirement barrier

Keep the live replacement entry gated while extending the synthetic broker and real-TLS loopback fixtures. Reuse the current source actor, listener, candidate pin, and join machinery.

1. Validate the incoming replacement projection against the exact current source, binding, old delivery, nominated target TLS observation, pin and request, next delivery generation, revision, and authority window. Require the broker's new projection to have output readiness cleared. A first attachment, same-delivery revision, confirmed transport loss, and replacement have distinct transitions.
2. In one serialized actor turn, close old media admission and remove the old connection and its send capability. Drop its plaintext expiry ledger, partial delivery assembly, and any sealed pacing or `WouldBlock` slot. Take the existing committed-source fence and retain the same PCM handle, source period, sequence, timestamps, and source identity. Keep the shared listener open. Give delayed close notifications and old pipe replies bounded, connection-scoped custody. A confirmed replacement retirement never creates reconnect grace.
3. Transfer candidate custody once. Quiesce and join actual candidate setup work before the source actor adopts its QUIC object. Keep the sole listener reader and bounded candidate ingress. A busy candidate or delayed close notification must not make the active media loop wait on an unbounded join. Send exact native authority acknowledgement only after the old send path is gone and the target has been adopted, with the target still media-disabled. A terminal grant preempts this transition. If transfer or fencing fails after commit, keep new media closed and follow owned rundown or the actual target's detach policy.
4. Admit the target's existing authenticated `OUTPUT` signal only for the current receipt digest, delivery, renderer incarnation, and live grant. Recheck that the broker projection is still current and take the fresh `CommitFence` at output admission. Keep the committed path's original commit and correlated presentation age checks at the existing 60 ms source-admission bound.

Exit evidence uses actual loopback TLS plus deterministic pacing and socket fault injection. Force an old sealed packet to be paced, then blocked, and make the socket writable after retirement. Observe the send hook and assert zero old sends accepted by the kernel after the barrier and zero new media before retirement and matching output admission. Allow for packets accepted by the kernel before retirement to arrive late. Include delayed old close, repeated or stale projection, full control credit, candidate death before and after commit, failure to take the source fence, and Stop, revoke, or expiry during join. The PCM source instance, commit provenance, and sequence stay continuous in the successful case. Failed retirement yields no admitted replacement media or successful retirement acknowledgement.

## 3. Separate Android playback from a delivery and prove same-route renewal

- Move the existing renderer, ASRC, output clock, and accepted and presented source frontiers under the native audio-run owner. Make the socket, TLS observations, control correlation, and delivery reorder residue children of the selected delivery. Retain one media owner, with bounded candidate service alongside active I/O. Process candidate DNS, key generation and signing as cold work, and keep Binder and JNI control out of the AAudio callback. Route control through the native owner rather than waiting on the lock held by the current long-running `PLAY` call.
- When activating a new delivery, reject old-route media and callbacks by identity. Clear old delivery reorder residue while retaining the source frontiers and valid physical output state. Preserve already admitted, still-valid PCM in the renderer within the existing playback budget. Stop, revoke, and expiry close the callback gate. Reuse the existing fresh-anchor and discontinuity behavior when a real gap requires it. A retained renderer may still underrun, and a failed physical route requires its own output incarnation and readiness sequence.
- Make same-delivery renewal an explicit prerequisite for sustained H4. Verify the exact signed renewal receipt against the retained operation and its original Android BOOTTIME send anchor. Update only the deadline and revision of the existing source and delivery. Test rejection after expiry, stale or reordered replies, delayed signing, and renewal overlapping Stop or a switch trigger. Qualify renewal and output recovery independently before measuring prolonged switching.

Exit evidence includes first delivery through the reorganized owner, same-source renewal through the real control path, no renderer reopen on a healthy renewal, and no change to the existing PCM buffers, ASRC configuration, or callback work. Include a deterministic receiver case with delayed old packets and a forward source-frame gap.

## 4. Integrate H4 in two steps

### A. Explicit switch with a healthy incumbent

- Add a separately gated handover capability to the broker and worker. Generalize the protected pinned-issue path to validate incumbent origin separately from target. Match both connections, source binding, target TLS observation, request ID, current revision, and deadline. Keep the accepted N2 proof and signed receipt formats. Reject unsupported worker and broker combinations. First attachment retains its own admission checks.
- Start with an explicit switch trigger and one bounded candidate. Resolve on the selected network and bind the candidate UDP socket before connect. Warm fresh TLS and public control while the incumbent plays. Apply consent, route reachability, roaming, metering, Data Saver, and VPN rules before use. Keep the candidate out of PCM admission and the positive request slot while it is warming.
- Nominate from the current approved connection and pin the same candidate and Android network lease before the one potentially committing Supersede. Serialize it with renewal. Keep the same `AudioPhoneRequests`, exact signature and first-send time. Transfer that same socket and lease after commitment and retain custody through uncertain outcomes until actual I/O joins. Apply the native barrier and bind new OutputReady to the retained physical renderer.
- Make the exact current target the receipt recovery route. Retain one signing outcome independent of whether the old route can deliver its response. Use the exact-result lookup promptly once the target can answer, and test an early lookup and an old route that falls silent. Keep generic old-path RPC timeout out of a successful cutover's critical path. A miss remains unresolved and consumes no new request sequence. Ensure the target cannot play media before matched readiness and the receiver rejects early or stale packets.
- Stop closes local playback immediately. Preserve the existing negative control lane while candidate, commit and signing work is outstanding. During ambiguous commitment use the reviewed source-scoped Stop path with valid evidence, and report Windows denial and actual rundown separately. A local mute is an observation on Android.

Run the exact-reply loss, latched signing failure, stale revision, output invalidation and Stop-at-each-boundary cases through the composed system. Use the existing C#, Rust, Kotlin and Android test fixtures. The first acceptance target is a real switch in both directions with one source, one live renderer, one positive request, and one admitted media delivery at a time.

### B. Transport loss and bounded automatic switching

- Add recovery after actual native and broker Detach. A route callback can start investigation or candidate preparation. A callback cannot authorize a successor. Reconcile old-bound work to actual completion, then issue an eligible new request within the original surviving source or grace window. A committed target that fails follows its own detach path. Expiry closes both routes.
- After explicit switching and loss recovery are green, add measured hysteresis, cooldown, warm TTL, work and byte bounds, and bounded failure backoff. Drive preparation from transport progress and credible route events. Default-network changes and Wi-Fi signal strength alone cannot justify cutting a healthy selected path. Leave automatic preparation disabled in profiles without approved routes or measured policy values.
- Test silent blackholes, abrupt loss, flapping, rapid reverse switches, no reachable cellular endpoint, IPv4 and IPv6 mismatch, VPN and Data Saver transitions, stale callbacks, owner death, and lease loss while DNS or native I/O is outstanding. Verify that candidate work cannot starve active media or the negative lane.

## 5. Gate performance and production with measured results

**Healthy-path budget.** Preserve the existing number of PCM copies, queues, and owner hops, and add zero callback allocations, locks, Binder calls, polling, duplicate media or extra playback reserve. Count allocations, callback work, wakeups, CPU, contention, source age at offer, sealed pacing and blocked dwell, underruns, and radio traffic with the candidate off and during warming. Put diagnostics on existing bounded instrumentation paths and measure their overhead separately.

**Cutover budget.** Measure trigger to route ready, TLS, nomination and proof, broker commit, native retirement and join, receipt and OutputReady, first fresh PCM admitted, first rendered sample, and actual audible interruption. Keep warm, cold, abrupt-loss and silent-blackhole distributions separate. Log the delivery and output generations, accepted source-frame floors, rejected late packets and source discontinuities. Use the timestamps to shorten the longest serial segment that the trace establishes. Begin with candidate preparation off the cutover critical path and exact receipt recovery before considering transport or buffer changes.

**Physical method.** Use the same host, handset, actual source period and audio route, load, PCM stimulus and network profile for matched comparisons. Measure source-to-speaker and the audible gap on a common electrical/acoustic acquisition clock using identifiable stimulus markers. Record calibration, resolution, repeatability, counts, p50/p95/p99 and maxima, confidence bounds, interruptions, failures and excluded runs. Record actual granted AAudio behavior and compare speaker, wired and Bluetooth as separate profiles where applicable. Include concurrent workspace/video load, sustained playback, screen-off, battery and radio cost, and repeat the renewal run across the original 1,800-second ceiling with at least three committed renewals. Compare competitive baselines only where the same physical workload and measurement rig apply.

**Exit criteria.** Require zero authority, stale-media, dual-send, and rundown violations in the deterministic fault suite. Predeclare the measurement uncertainty and per-profile regression margins before each comparison. Reject meaningful latency, continuity, or resource regressions against the matched healthy reference, and treat unresolved tails as open evidence. The 60 ms source-admission rule is one software invariant. Acoustic latency and handover gaps need their own distributions. Gate production on separately authorized device results, the normal-speaker category/RAW and routing gates, and a demonstrated rollback to the prior qualified profile.

Commit each independently verified source increment to `main` and use the ordinary hosted checks. Keep the first-delivery and replacement feature gates separable so the prior first-delivery profile is available while H4 or H5 is still open.
